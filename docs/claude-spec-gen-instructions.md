I need to create a specification for my app to give to Claude Code to start implementing it. Can you help me?

I want to build a coding tool for personal use. I named it `Appsmith-CT​`. This is not like any other coding tool. The main focus of this tool is to automate the roles of people at a software development company. Like in the previous place that I worked on, the software development process basically went like the following.

---

A client comes to the office with a request to make a software solution, sometimes it is to computerize and automate a manual system they already have, or sometimes it is to rewrite/upgrade an existing legacy software system, or sometimes it is to create an entirely new software product that they are going to sell, or sometimes it is a management system or some type of a software system that only will be used with in the client's company internally. You get the idea.

Our `BA` (Bussiness Analyst)​ and the `Software Architect`​ have talks and interviews with the client back and forth. And finally our `BA`​ confirms the scope of the project and create a set of functional requirements, and some other documents (only if necessary), and submit them to the `Software Architect`​. I will refer to the `Software Architect​` as `SA`​ moving forward.

Our `SA`​ analyze the set of requirements and plans the architecture this new software solution should have. I have no idea how he comes up with the correct architecture for the software solution. Sometimes he follows a process called `DDD` (Domain Driven Design), sometimes he follows a process called `OOD` (Object Oriented Design), sometimes he pulls the architecture out of thin air. LOL!. Somehow he comes up with an appropriate architecture for the software solution. This software architecture can be a huge monolith if what we are building is a standalone desktop application, or it can be a microservices architecture. Most of the time it is more leaning into the microservices architecture with some of the services having monolith type properties. Sometimes it is a web application with just a `FE`​ (Front End) and a `BE`​ (Back End), and then later iterations we break off the `BE`​ into other services, etc. etc. But for the most part I worked there the `SA` always came up with a architecture that has a `FE`​ (Front End) and a `BE`​ (Back End) and the `BE`​ is broken down into two or three services (at least at the beginning). The `SA` and `Tech Leads` comes up with appropriate technology stacks and `SA` comes up with the appropriate deployment strategy as well. The `SA` then hands over each component (`FE`, `BE` services if it is a microservices architecture, and components of the monolith if it is a monolith architecture) to each `Dev Team`. Each `Dev Team` is lead by a `Tech Lead`. The `SA` gives a list of requirements each of these component must satisfy in order to be considered completed. Each `Dev Team` is only given the requirements for the component they are working on. The other parts of the system are completely abstracted away from each team. Only the `SA` have the full picture. This is done so the `Dev Team` can better focus on a small part of the system. For an example the `Dev Team` that is responsible for creating the `Cost calculation and Billing` service, they are only given how they are going to recieve the data they need to calculate the cost (maybe these data is published to a queue when some event happens in the system) and the structure of these data packets, and the responsibility of the `Cost calculation and Billing` (maybe this service needs to keep track of all the expenses and the revenue of the system, and then calculate the profit, and then send a report to the `Accounting` service, etc. etc.). The `Dev Team` is not given any information about how the other services work, or how they are going to use the data they are sending to them. They are only given what are the data their service recieves, and how they are going to recvieve (maybe using a queue or a REST API call), and what are the data that it should output and how they should output these data (by calling another API call or publishing to a queue or some any other way?), and whether they should persist these data for future use or not. The `SA` do not care about "HOW" the `Dev Team` is going to implement their component, as long as they satisfy the requirements. The `SA` only care about "WHAT" the `Dev Team` is going to implement. The `SA` do not care about the implementation details of each component, as long as they satisfy the requirements. The `SA` only care about the overall architecture and how each component fits into the overall system. Another example is that the `FE` only recieves how the web app should look like and the OpenAPI specs of the APIs and different base URLs it should use.

I am going to refer to `Tech Lead` as `TL` moving forward. Most of the time the tech stack has already been decided with a talk with the `SA`. `TL` re-evaluvate these decisions with the `Dev Team` and finalize on the tech stack. If the component they received is a monolith component then the `Dev Team` basically doesn't have a say in the tech stack. The `TL` will break down the requirements into smaller tasks and assign them to the `Dev Team` members. Usually a `Dev Team` consist of 3-4 people apart from the `TL`. There can be serveral types of developers in a `Dev Team` like the `SE` (Software Engineer), `SSE` (Senior Software Engineer), `Intern` (Software Engineer Intern). These roles are devided based on their experience and competency. The `TL` will assign the tasks to the `Dev Team` members based on their experience and competency. The `TL` will also be responsible for reviewing the code and making sure that the code is of high quality and follows the best practices. The `TL` is also responsible for coming up with the internal architecture and code structure for the individual service they are building. If the component is part of a monolith then most of the time `SA` gives a set of architecture rules these teams should follow. If it is microservice then the `TL` has more freedom to choose an appropriate architecture. But in our company, there was a default sliently agreed upon starting architecture and the code structure for the backend services. Some of them sticked to this default architecture for the entire life of the service. Some of them derived from this a bit depending on the situation. But comming up with an internal architecture was cruical when the `TL` assign tasks with minimal to no overlap. The `TL` was also responsible for making sure that the devs are documenting the code properly. And writing unit tests (unit tests are developer responsibility). The `TL` also review their PRs and merge them or request change when necessary. And `TL` will write the necessary tests to test the entire component end to end.

Once the service is implemented and tested, the `TL` will hand over the service to the `SA` for integration with the other services. The `SA` will then deploy the integrated system to a staging environment and test the entire system end to end. The `SA` will then hand over the system to the `QA` team for further testing. The `QA` team will test the system and report any bugs or issues to the `SA`. The `SA` will delegate the bug fixing to the appropriate `Dev Team`. Once the bugs are fixed, the `SA` will deploy the system to production. The `SA` will then monitor the system in production and make sure that it is running smoothly. If there are any issues, the `SA` will delegate the bug fixing to the appropriate `Dev Team`.

I forgot to mention that in the begining `BA` and `SA` will also come up with a project plan and a timeline for the project, and the milestones that need to be achieved. A milestone is something that can be demonstrated to the client in action. May be it is a scaffolds of the entire system with minimal basic functionality. May be it is planned feature. You get the idea right. So our sprint was usually 2 weeks long but sometimes it is longer in the early sprints. The `SA` will do the most heavy lifting in the first sprint. Sometimes the first sprint takes like 2 months. Because we only consider a sprint is ended once we have something to show to the client. So the `SA`'s job in process I described above mostly only happens in the first sprint. After the first sprint, the `SA` will only be involved in the project when there is a need to change the architecture or when there is a need to add new features that require changes to the architecture. The `BA` will also be involved in the project after the first sprint, but mostly for gathering new requirements from the client and for clarifying any doubts the `Dev Team` may have regarding the requirements. We only accept changes to the requirements at the end of a sprint. If a requirement is changed then the `SA` will have to re-evaluate the architecture and make necessary changes and delegate them to the Dev Teams. The `TL`s' and `Dev Team`s' and `QA`s' job will be the same in the later sprints as I described above. After the first sprint, the `SA`'s job will be mostly to monitor the progress and integrate the components and make sure that the system is working as expected.

---

With `Appsmith-CT` I intend to simulate the above entire process using LangChain and LangGraph. There will be a chat agent that basically chat with the user and ask questions to gather requirements. And then when the user feels like they have provided enough information, they can trigure the pipeline. The first step will be to figure out the functional requirements from the user's input. There will be a `BA` agent that will analyze the user's input and come up with a set of functional requirements. The `BA` agent will also come up with the project milestones. We really don't care about the timeline here. The `BA` agent will then pass the functional requirements and the milestones to the `SA` agent. The `SA` agent will analyze the functional requirements and come up with an appropriate architecture for the software solution. The `SA` agent will also come up with a list of components that need to be implemented and the requirements for each component. The `SA` agent will then pass the list of components and their requirements to the `TL` agents. Each `TL` agent will be responsible for a component and will break down the requirements into smaller tasks and assign them to the `Dev Team` members. The `Dev Team` members will then implement the tasks assigned to them and submit their code for review. The `TL` agent will review the code and merge it if it meets the requirements. Once all the tasks for a component are completed, the `TL` agent will hand over the component to the `SA` agent for integration with other components. The `SA` agent will then deploy the integrated system to a staging environment and test it end to end. Once the system is tested, it will be handed over to a `QA` agent for further testing. The `QA` agent will test the system and report any bugs or issues to the `SA` agent. The `SA` agent will delegate bug fixing to the appropriate `Dev Team`. Once all bugs are fixed, the user will be notified that the system is ready for deployment.

The main thing I want to experiment with `Appsmith-CT` is to see if we can use smaller LLMs to simulate the roles of different people in a software development company and see if we can automate the entire software development process using LangChain and LangGraph.

But my problem is that it is a bit expensive for me to purchase access to these frontier AI models. So I want to see if we can use smaller self hosted LLMs that specialize in different roles to simulate the entire software development process.

I am mainly targeting the `prismml bonsai` LLM for this project.

I haven't thought about how I'm going to architect `Appsmith-CT` yet. I will leave that to you to come up with an appropriate architecture for the application. I will also leave it to you to come up with an appropriate tech stack for the application. I am open to any suggestions you may have.
